Same Bot, Two Games

08 Oct 2026 · 4 min read · agents llm search

TL;DR
  • Playing White with only a play_move tool, a local 27B model lost to a deterministic two-ply bot by checkmate on move 33.
  • With a depth-4 alpha-beta search choosing White’s moves, the same bot was mated in 17.
  • Search depth decided the result. An evaluation bonus I expected to matter did not.
  • The winner is a program I wrote, not the model. The model running that search itself is a hypothesis I have not tested yet.

This is the chess half of the harness I built for CMU’s 11-768. The harness itself, and the bugs that taught me the most, are in The Harness Is the Product.

The opponent is a deterministic engine that looks two plies ahead: its own move and White’s best reply. I played White against it twice.

Before: the model picks, a tool plays

The model sees the board as text, picks a move from the legal list, and calls play_move. That was its only tool. It made 36 calls for 33 moves. Three were rejected as illegal rook moves, even though the legal moves were listed in front of it.

The game turned in a few moves. On move 14 the model played Qa6, and Black took the queen with a rook. The two-ply scorer I used to rank moves put Qa6 31st of 35 legal moves, and it cost nine points of material in one turn. By the end White had only its king.

After: a deeper search behind the same game

Then I replaced the model with a program: an alpha-beta search that scores every legal move and plays the best one. Same bot, same server.

Depth 2 sees as far as the bot does, and it drew. One extra ply was enough to win, and a second one made the win quick.

Material stayed within two points of even the whole game, so the win came from a mating attack. It ends Bb6+ Qxb6 Qxf8#: the two-ply bot took a bishop sacrifice, and White’s queen mated. Seeing that line takes four plies, which a two-ply search does not have.

I added a bonus to the evaluation for pushing the enemy king toward the edge and expected it to matter. It did not. Without it, depth 4 still mates in 17, and depth 3 wins in 26 moves instead of 53. The game is deterministic, and re-running depth 4 reproduced it move for move.

A number I almost reported
I wanted to report how often each player picked the best move. That depends on who decides what “best” is. Judged by the depth-4 search, the model picked its top move in 7 of 33 turns (median rank 4), and the search did so in 17 of 17, but only because it is that search. Judged by the two-ply scorer, the model matched in 9 of 33 and the winning search in only 4 of 17. The two-ply scorer is not what wins games, so I would not use agreement with it as a quality score for either player.

What this does and does not show

Every move in the winning game came from my search program. Giving an agent somewhere to compute changes what the system can do without changing the model at all. It does not show that the model can write or run that search itself. Each result is one game against one deterministic opponent.

The next experiment

The harness already has what the model would need to run the search itself: a run_python tool, a simulate_move tool that plays out a move without changing the real game, and skills that load instructions on demand.

My guess is that the model wins far more often with those tools, but I have no data for that yet. I can name ways it fails just as easily: the model might write a wrong search or skip the skill (I have seen it skip a skill before), running code costs steps and tokens that a step limit or compaction could cut short, and a slow search could hit the sandbox timeout.

To test it I would run a batch of games with and without the skill, with the same model and settings, and count wins, moves to mate, tokens used, and how often the model reached for the skill. A loss would still tell me something: whether the bottleneck is the model, the skill text, or the tools.
