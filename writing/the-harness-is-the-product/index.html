The Harness Is the Product

01 Sep 2026 · 6 min read · agents llm engineering

TL;DR
  • I built an agent harness from scratch for CMU’s 11-768 (AI Agents) and ran a local 27B model through a bug fix in a chess server, a real Django issue, and games of chess.
  • On the Django issue the fix took 5 model calls. Checking it took 29.
  • Compaction kept the prompt under 5,900 tokens across 38 calls. The server’s own counts show each compaction cut the prompt by 31 to 50%.
  • Most of what looked like “the model is weak” was a bug in my harness.

A harness is the code around a model. It sends a prompt, parses the tool calls that come back, runs them, and feeds the results in again. It also owns the tool definitions, the memory, the skills and the stop conditions. For this course I wrote one from scratch and pointed a 4-bit Qwen3.8-27B at it, served from my home GPU server. Nothing here needed a frontier model.

Three layers

Skills use progressive disclosure. The prompt lists each skill in a line, and an invoke_skill tool loads the full instructions only when the model asks for them. Compaction is the memory layer: when the prompt crosses a threshold, the model writes a working memory of the older part. The task and the most recent step stay word for word.

A bug fix that ran out of steps

The first job was a bug in the chess server that only showed up at the end of a game. The agent read the server code and the tests, wrote a reproduction, fixed it, and ran the suite: 9 passed. It used all ten of its allowed calls, and the budget ran out one call before the final message.

The agent did the work and the run still failed, because I had set the step limit without checking how long the task was.

A Django issue, and where the calls went

The second job was django__django-15368 from SWE-bench: bulk_update() mishandled a plain F() expression and wrote the text of the expression into the SQL instead of the column. The fix is one line.

4

Most of the agent’s effort went into working out how to check its own work. A harness can help there with readable tool output that does not flood the prompt, and with enough steps to finish.

What compaction did to the prompt

I set the compaction threshold at 6,000 tokens. The harness compacted four times, and the prompt never went past 5,890 tokens.

Compaction before call Harness estimate Server count, call before to call after
15 5,352 to 2,006 5,642 to 2,986 (47% less)
22 5,549 to 2,386 5,812 to 3,372 (42% less)
29 5,202 to 2,648 5,387 to 3,736 (31% less)
36 5,164 to 1,952 5,890 to 2,933 (50% less)

My harness estimates tokens roughly, so I trust the server’s column. It is less flattering: the estimates suggested cuts of 50 to 60%.

The first working memory had the objective, the file and line to change, the edit already made, and the approaches that had failed: the sed command that broke on quoting, and test scripts that failed on app-label setup. Both survived the compaction, so they were still in front of the model afterward.

What I did not measure
I did not run the same task without compaction, so I cannot say how many tokens it saved or whether it changed the number of steps. All I can say is that the agent kept working through four compactions and submitted a patch.

Five bugs that looked like the model

  1. The skill nobody called. A submit skill existed, but the prompt only said skills were available. The model finished without it, no patch file was written, and the run failed. One required sentence fixed it: if a skill applies to finishing, invoke it before the final message. Even so, at call 34 of the Django run the model tried to wrap up in prose. The harness replied that no tool had been called, and the next call was invoke_skill. I cannot tell how much of that was the prompt rule and how much was the nudge.
  2. Tool schemas are code. Mine had unmatched braces, a set literal where a dict belonged, a missing key, and descriptions that lost their spaces when strings were joined. A tool description is part of the prompt, so a broken one breaks the prompt and nothing crashes to tell you.
  3. Parallel calls on shared state. A model can send two play_move calls in one response. The harness has to allow one move per turn and refresh its view of the game after any code the model runs.
  4. The step budget from the chess-server fix above.

What I would tell the next person

  1. The model only knows what the tool results tell it. Test that path like a public API.
  2. Tool descriptions, skill descriptions and system prompts are the controls you have. Review them like code.
  3. If you want a behaviour, require it in the prompt. A skill being available does not mean it gets used.
  4. Budget steps for checking the work, not only for doing it.
  5. Compact old work, keep the task word for word, and never split a step from its results.
  6. Save every trajectory. That is how you tell a model problem from a harness problem.
